# Supabase PostgreSQL Migration Plan

## Scope and verified starting point

This document defines the staged migration of Golden Prime PG from its current TiDB/MySQL production database to the connected Supabase PostgreSQL project. It is a **migration plan and readiness record**, not a cutover record. TiDB remains the production source of truth until every target validation and role workflow passes and a final change window is explicitly approved.

The accessible target project is active and healthy on PostgreSQL 17. The reviewed initial schema migration has created the required **22 empty tables** in the `public` schema, including foreign keys, unique constraints, indexes, and 16 automatic `updatedAt` triggers. No target data import, runtime connection change, Supabase CLI initialization, project linking, or credential change has been performed. The target has standard Supabase extensions available; the design does not depend on an additional extension.

|---|---:|
| Users / Owners / Managers / Tenants | 5 / 2 / 1 / 2 |
| Buildings / staff assignments / floors / rooms | 1 / 1 / 5 / 3 |
| Tenant profiles / active and historic allocations | 2 / 3 |
| Rent payments / tenant charges / reminders / notifications | 2 / 1 / 2 / 5 |
| Owner settlements / change-audit records | 1 / 1 |
| Electricity, expenses, operating costs, transfers, service configuration, export history, government-electricity payments, Manager adjustments | 0 each |
| Rent expected / paid | ₹13,000 / ₹13,000 |
| Tenant-charge expected / paid | ₹300 / ₹300 |

The source integrity checks found zero orphan rooms, tenants, allocations, rent payments, and tenant charges, and zero overpayments in rent, electricity, and tenant-charge records. These values become the minimum post-import reconciliation baseline. The exact values must be re-read immediately before the final import because TiDB may legitimately change while the target schema is prepared.

## Compatibility decision

The existing MySQL schema and `server/db.ts` cannot be pointed at PostgreSQL by changing a connection string. The application uses the MySQL Drizzle dialect, `mysqlEnum`, `onDuplicateKeyUpdate`, MySQL insert-result identifiers, and `onUpdateNow`. The migration must introduce a separate PostgreSQL schema and explicit data layer adaptation before runtime cutover.

| Source concern | PostgreSQL target decision | Validation requirement |
|---|---|---|
| Integer primary keys with auto-increment | Use `integer generated by default as identity`; import existing numeric IDs explicitly, then reset each identity sequence above the imported maximum. | Imported parent and child IDs match exactly. |
| `mysqlEnum` status and role columns | Use named PostgreSQL enums with the complete current value sets. The `exportType` enum begins with `tenants`, `rent`, `electricity`, `expenses`, `selected`, and `complete`. | Every source value is accepted and preserved. |
| `timestamp` columns | Use `timestamptz` for `createdAt`, `updatedAt`, review, notification, and audit timestamps; preserve all existing instants as UTC. | Timestamp equality is compared as UTC instants. |
| `date(..., mode: string)` business dates | Use PostgreSQL `date` with Drizzle string mode. | `YYYY-MM-DD` values remain unchanged. |
| `updatedAt.onUpdateNow()` | Install a small `BEFORE UPDATE` trigger that updates `updatedAt` for the same tables where the source schema currently updates it. | Stale-write and update tests still reject or detect overwritten records. |
| Money stored as integer paise | Retain `integer` paise values for compatibility with existing TypeScript calculations and API contracts. | Per-table expected, paid, and outstanding totals reconcile exactly. |
| `snapshotJson` audit snapshots | Retain as `text` in the first migration to preserve source payloads byte-for-byte; do not coerce historical data to `jsonb`. | Recovery-audit parse and undo tests pass. |
| MySQL upserts | Replace each `onDuplicateKeyUpdate` with a target-specific `onConflictDoUpdate` or `onConflictDoNothing` using the matching unique key. | Rent-cycle, reminder, notification, bill, settlement, and assignment idempotency tests pass. |
| MySQL `insertId` result handling | Replace insert-result access with PostgreSQL `returning({ id: table.id })`. | Creation, allocation, transfer, deletion-audit, and account-creation tests pass. |

## Target schema inventory

The first PostgreSQL migration will create the same 22 operational tables and all defined foreign keys, unique constraints, and indexes. The source naming is intentionally preserved in this first migration to minimize contract risk in existing tRPC procedures, exports, offline snapshots, and audit restoration.

| Dependency order | Tables |
|---|---|
| 1. Identity | `users` |
| 2. Building boundary | `buildings`, `staffAssignments`, `floors`, `rooms`, `tenants` |
| 3. Occupancy and billing | `roomAllocations`, `rentPayments`, `tenantTransfers`, `electricityBills`, `tenantCharges` |
| 4. Expenses and settlements | `expenses`, `operatingCosts`, `ownerSettlements`, `governmentElectricityPayments`, `managerCreditAdjustments` |
| 5. Supporting operations | `serviceCharges`, `tenantServices`, `reminders`, `managerNotifications`, `exportHistory`, `changeAuditLogs` |

Every table that has `buildingId` keeps its foreign key to `buildings`, and every existing `onDelete` behavior remains unchanged. This preserves the application’s isolation model: Owner access derives from `buildings.ownerId`, Manager access from `staffAssignments`, and Tenant access from the tenant profile and active allocation. Password hashes are copied only as existing hashes through a server-side protected path; no plaintext password, database password, access token, session value, or Supabase credential is exported or committed.

## Source-to-target transfer design

The target import will be an explicit, one-way, idempotent job that uses privileged server-side database connections only. Browser clients and publishable API keys are not migration credentials. The job will read TiDB in dependency order, transform only database-dialect representations, insert explicit IDs in PostgreSQL, and record a non-sensitive migration manifest containing run time, source watermark, table row counts, and aggregate checksums. TiDB does not support the MySQL `START TRANSACTION READ ONLY` form in this environment, so the transfer uses a repeatable-read transaction and a code path limited to `SELECT` statements; it never issues a source mutation.

The first target load has completed and was repeated successfully with duplicate-ignoring primary-key inserts. Its source-to-target table counts reconcile exactly, its critical allocation/payment/charge foreign-key checks have no orphaned records, and its imported serial sequences were reset to each table's current maximum identifier. This confirms the target-copy process, but it does **not** authorize runtime cutover: the active application still uses the MySQL Drizzle driver and TiDB connection.

The runtime adapter is now implemented and validated in the controlled environment. It selects the existing TiDB path unless the server-only database selector is explicitly set to `postgres`; the PostgreSQL path uses the protected Supabase connection string and `node-postgres`, never a browser key. The data-layer conversion includes PostgreSQL conflict targets and `returning` values for all migrated upserts, inserts, audit writes, and optimistic corrections. A final production checkpoint will switch the deployed application only after the user confirms the maintenance window.

The user approved the production change window on 2026-08-25. The final synchronization and target integrity query completed before publishing, and the server-only selector is set to PostgreSQL for the cutover release. TiDB remains preserved as the rollback source. A rollback requires restoring the preceding TiDB-backed checkpoint and changing only the server-side selector; no customer data must be deleted from either database to reverse the application connection.

| Transfer stage | Required behavior | Failure behavior |
|---|---|---|
| Extract | Read source tables in deterministic primary-key order, without printing customer records or hashes to logs. | Stop before target writes if extraction cannot establish a consistent watermark. |
| Load | Insert parents before children inside target transactions; use explicit imported IDs and batched parameterized statements. | Roll back the affected target transaction and retain the TiDB source unchanged. |
| Reconcile | Compare table counts, minimum/maximum IDs, foreign-key orphan counts, enum distributions, money aggregates, and audit/receipt URL counts. | Mark the run failed and do not alter application runtime configuration. |
| Re-run | Use a migration-run identifier and conflict-safe imports so a failed dry run can be retried after the isolated target is cleared or repaired. | Never delete or rewrite TiDB production data. |
| Cutover | Re-read source baseline immediately after a short write freeze, import the final delta, verify role workflows, then switch the server-only runtime connection. | Restore the previous TiDB server variable and redeploy the already validated TiDB runtime. |

Receipt, meter, QR, and document fields contain storage URLs, not file bytes. Their exact URL references are migrated as text, while the underlying S3 objects remain in their current managed storage. The migration will not move or duplicate object bytes unless a later storage migration is separately requested and validated.

## Runtime and schema migration approach

The codebase will keep the current `drizzle/` MySQL schema and runtime untouched while target preparation is in progress. A parallel `drizzle-pg/` directory will hold a PostgreSQL schema, a separate Drizzle configuration, and reviewed SQL migration output. The PostgreSQL runtime will use `drizzle-orm/node-postgres` with the `pg` driver and a server-only `SUPABASE_DATABASE_URL` deployment secret. The final runtime connection must use the appropriate Supabase pooled connection mode for the autoscaling deployment and SSL; the direct connection is reserved for migration and management tasks when the network supports it.[1] [2]

Schema changes will be kept in version-controlled migration files and applied in a single coordinated path. Supabase documents that remote ad-hoc schema edits bypass migration history; therefore target DDL will be applied through the reviewed migration mechanism rather than the dashboard.[2] Drizzle supports PostgreSQL through `node-postgres`, and the application changes will use PostgreSQL-native conflict targets and returning clauses rather than MySQL result semantics.[3] [4]

## Cutover gate and rollback

The following gates must all pass before a production connection switch is proposed:

1. The PostgreSQL schema is created successfully in the target with all 22 tables, foreign keys, indexes, enum values, and update triggers.
2. A dry-run import reconciles every table count, ID range, relation check, money aggregate, receipt URL count, and change-audit payload count against the current TiDB baseline.
3. Fresh full-suite tests, TypeScript validation, and a production PWA build pass after the PostgreSQL data layer is enabled in an isolated environment.
4. Phone/password sessions and critical Manager, Owner, and Tenant workflows pass against PostgreSQL: building selection, room allocation and transfer, billing and partial payments, receipt review, upload URL visibility, deletion undo, exports, and offline read-only snapshots.
5. A short source write freeze, final delta import, fresh aggregate reconciliation, and an explicit user-approved change window are completed.

The rollback is intentionally simple: TiDB is not deleted, paused, or overwritten during this project. If validation or the first PostgreSQL production release fails, the server-only database variable is restored to the TiDB connection, the known-good TiDB application release is redeployed, and PostgreSQL is retained only as a failed migration target for forensic review. No reverse data replication is attempted during the initial cutover.

## Required secure input before runtime work

The current connector can inspect and administer the target project, but the application runtime needs a dedicated, server-only PostgreSQL connection string or equivalent protected database credential. The URL and publishable key are insufficient for this task. The credential must be supplied through protected project configuration or an authenticated connection workflow; it must never appear in a chat message, source file, Git history, browser bundle, export workbook, or log.

The suggested `supabase login`, `supabase init`, and `supabase link` commands are not required for the assessment and have not been run. If the CLI path is chosen later, login must be completed interactively by the authorized account, and linking must occur in a dedicated PostgreSQL migration directory only after the local migration files are reviewed.
